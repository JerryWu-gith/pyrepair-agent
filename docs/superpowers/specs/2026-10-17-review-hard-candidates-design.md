# Review 隐蔽错误挑战集：六题十二候选设计

日期：2026-10-17。

状态：用户已审核；沿用 Inline Execution 完成离线实现、校准、独立审查及最终回归，2026-10-19 完成交付整理。尚无新模型结果，真实 API 调用为 0。

## 1. 要解决的问题

上一轮固定六候选的 36 次真实对照中，无说明组判断正确 16/18，有说明组 18/18；两组都拒绝了全部 9 次错误候选判断。但错误候选主要是硬编码单个测试输入，难以检验 Review 对更隐蔽缺陷的识别能力。

本阶段增加**契约明确、可见测试通过、独立验收能复现错误**的候选，而不是增加相同简单题的重复次数。目标是建立可信的挑战集与离线证据；不是先追求某个模型分数。

已有依据：[真实对照结果](../../review-contract-live-results.md)、[工程日志步骤 24](../../evaluation-v2-engineering-log.md)。

## 2. 范围与不做的事

包含：

- 六个既有任务，每题一份正确参考与一份非单样例硬编码错误，共十二候选。
- 新集合单独保存正确参考、错误补丁、增强隐藏验收、来源和标签理由。
- 准备包绑定实际选择的候选集合及任务资产；修改已绑定资产后拒绝直接用于新调用。
- 报告按集合元数据展示实际任务数和候选数，保持既有实验可离线读取。
- 离线正反例校准、输入隔离测试、历史保护、文档及问题记录。

不包含：

- 真实 API 调用、付费续跑、重新生成模型修复补丁、扩大上一轮 36 次预算。
- 新 Repair 工具、Review 提示词优化、修改生产 Agent Loop、Policy 或 Verifier。
- 真实开源缺陷、容器化、自动拉取外部仓库、额外依赖、服务化或新模型。
- 将这些题标为 holdout，或将人工参考包装成模型成绩。
- 改写原任务、旧六候选、旧隐藏验收或旧运行成绩；提交、合并、推送、PR、删除工作区。

仍使用 evaluation-v2 托管 detached HEAD worktree。普通 CLI 的运行方式不变。

备选路线是直接引入真实开源缺陷，但它还需要缺陷版本定位、依赖环境和复现协议，范围更大。本轮先采用用户已选择的独立开发挑战集。

## 3. 六题与具体判别点

前两题用于中等难度的边界/归一化校准；后四题关注数值精度、跨模块语义或状态副作用。“更难”指比旧硬编码候选更有区分价值，不声称已经测得模型更难识别。

| 原任务 | 正确参考要求 | 错误候选机制 | 新增判别证据 |
| --- | --- | --- | --- |
| case_04 | 仅 1 <= page <= total_pages 有效 | 修上界时把下界改成 0，放行第 0 页 | (0,3) 必须 False；(-1,3)、(1,0) 也 False；(1,1) True |
| case_13 | 去掉首尾空白并忽略大小写 | 只 lower，不 strip；普通 true/false 可通过 | `" True "`、`"\tTrUe\n"` 应 True；带空白 false 应 False |
| case_15 | 契约内十进制金额精确转换成整数分 | 历史 Decimal 乘 100 写法受上下文精度影响 | 长金额及 context 精度 2/28/64；沿用已有 18 项精度反例证据 |
| multi_orders | 所有项先求整数分小计，再对总额应用折扣并向下取整 | 改成逐项折扣、逐项取整后相加；整百金额看不出差异 | [(1,1),(1,1)] 的 vip 总额为 1，不是 0；[(101,1),(101,1)] 为 161，不是 160 |
| multi_inventory | 合法预订扣精确数量；失败不改库存；取消只归还一次 | 先扣库存，再检查不足并抛错，没有回滚 | 库存 3 预订 4 后应报 ValueError 且仍为 3；另测恰好耗尽、多个预订与重复取消 |
| multi_time | 主流程与公开辅助函数均符合 UTC 契约 | parser 保留原偏移，formatter 再转 UTC；主流程正确但 parser 输出不是 UTC | 直接调用 parse_timestamp，断言 utcoffset() 为 0 且真实时刻正确；不能只比较 datetime 相等 |

所有负例都要通过原可见测试，且失败点必须在**既有公开契约以内**。不以无时区时间等已明确不支持的输入否定候选，也不添加模型看不到的新业务要求。

具体补丁仍需实施时实际运行校准；表格不是已通过测试的声明。若标签不成立，停止准备并记录，不隐藏失败或在模型回答后改标签。

### 金额参考的来源

正例复用此前明确标注的人工校准方案：Decimal.as_integer_ratio 后使用整数运算，不进行受 context 精度影响的 Decimal 乘法。负例取自此前排除的历史 Decimal 乘法候选，保留原始来源与哈希。

它在旧六候选中仍然是“排除诊断”，不更改那份清单；在这个新集合中才成为正式反例。旧 54/54 仍只表示旧有限验收下的结果。

### 库存参考的额外校准

旧参考没有显式验证 quantity 的整数类型。新正例需要同时保证：非整数（例如 1.5、字符串）、非正整数、超过库存的请求均报 ValueError 且库存不变；有效请求正确扣减并支持幂等取消。

新的标签不依赖 bool、int 子类等此前未明确的细节；如果后续确实需要以这类边界决定正反例，先澄清契约，不在验收中私自加要求。此次先使用明确的普通整数/浮点数/字符串样例。

## 4. 文件组织与来源

新增文件布局：

```text
benchmarks/
  manifest_review_hard_v1.json
  review_cases_hard_v1/
    README.md
    manifest.json
    private/
      case_04/
        gold.patch
        wrong.patch
        hidden_tests/test_acceptance.py
      case_13/                 # 同样三类资产
      case_15/
      multi_orders/
      multi_inventory/
      multi_time/
```

任务 manifest 放在 benchmarks 根目录，使既有安全路径解析仍能使用 cases/...、eval_cases/... 和 eval_descriptions/...，无需引入 `..` 路径或复制一份 public 树。

新任务 manifest 仅列这六题，保留原 task ID，在本集合记录 revision=2、source_kind=synthetic、split=dev 及原任务来源；private_path 指向新目录。原 manifest_v2.json 不变。新隐藏文件保留原验收的意义，并增加上表判别条件；不写回原 eval_private。

候选 ID 统一使用 `hard_v1_<case_id>_positive` / `hard_v1_<case_id>_negative`，避免与旧集合混淆。候选清单指向各自的新 gold.patch/wrong.patch；不为方便而引入第二份同内容补丁。

每个候选保存：任务 ID、正反标签、机制分类、补丁路径、来源类别、来源路径或说明、可用的原始 SHA-256、契约依据。手工构造的内容明确标注人工参考或人工变异，不虚构历史模型来源。模型不会收到这些标签或分类。

## 5. 离线校准流程

1. 校验集合清单、六题十二候选关系、标签类型、安全路径和实际资产存在；同题正反例使用同一公开契约与原始故障。
2. 在只含公开源码、可见测试、TASK.md 的临时副本复现 baseline，捕获可解析的真实断言失败；不安装隐藏测试后再采集模型故障输入。
3. 每份补丁在新的独立副本中应用，执行路径规则与可见测试；可见失败、收集错误、环境错误、跳过测试等不能算有效反例。
4. 安装新集合的独立隐藏验收，正确参考必须全部通过；错误候选必须至少一个真实 AssertionError，且声明的必需测试节点完整。
5. 使用现有 Review 专用异常证据插件，拒绝将 FileNotFoundError 等运行异常冒充断言失败；执行前后检查源文件/测试哈希，防止候选改验收文件。
6. 全部十二候选成立后，才写出带摘要的 ready prepared.json；失败保留诊断目录，不生成可供 live 使用的准备包。

增强验收全部放入新 private 隐藏文件，尤其把金额精度检查纳入新题的正式隐藏验收，不依赖“先过旧 hidden、再在额外 precision 阶段失败”的特殊标签漏洞。旧准备器的金额诊断分支可继续服务旧集合，不扩大到新集合。

原始失败、候选 Diff 与公开说明仍是模型输入的全部业务信息。隐藏测试、参考答案、标签、分类和失败反例不进入 Repair/Review 消息；目录隔离不是 OS 沙盒，只用于可信自建资产。

## 6. 修正资产指纹绑定

### 已发现的原因

prepare 的 --fixtures 参数已支持自定义目录，但 review_runtime() 始终哈希 ROOT/benchmarks/review_cases。换成新集合后，如果仍使用旧逻辑，就不是在校验真正选择的集合。

现有默认目录的 36 次实验仍有完整摘要与来源证据，不因此被推翻。新扩展必须先通过失败测试复现这个缺口，再修正数据传递。

### 要达到的行为

- prepare 将**实际选择的 fixtures 目录**传入身份计算，并记录任务 manifest 及所选任务资产绑定；不能假设只有一个固定集合。
- 新准备包记录资产定位信息、manifest 摘要、完整 fixture 摘要，以及所用公开源码/契约/验收的任务指纹。
- 仓库内资产以仓库相对路径定位；现有单元测试使用仓库外临时集合时，显式记录该临时位置，不把它误映射成默认目录。移动外部临时资产后须重新准备。
- load_prepared 在任何模型客户端初始化前，检查运行时及实际绑定资产。更改当前集合补丁、说明、隐藏测试、清单等必须拒绝；变更无关的旧候选目录不应误伤新的独立集合。
- 不通过删除校验、只信 prepared 自称的标签、或对读取异常静默回退默认目录解决问题。

新准备包增加版本化的资产绑定字段，沿用已有顶层协议的兼容分支；旧准备包缺少新字段时使用原读取规则。源码改变后，旧 ready 包可能因源码指纹变化而无法重新 live，这属于预期保护；**历史 run 的 report 必须仍可离线读取和重建**，它不依赖当前源码与当时相同。

摘要是误改检测与复现工具，不是抗恶意修改的数字签名。此轮不建设通用数据集注册系统。

## 7. 集合元数据与报告兼容

当前报告直接写“三题”和“这六候选”，新集合不能沿用该固定说明。

新集合提供经过校验的集合 ID `review-hard-v1`、source_kind=synthetic、split=dev，以及候选到任务的映射。任务数与候选数从实际映射推导，不盲信自由填写的计数字段。集合信息进入 prepared/实验 manifest，**不进入模型消息**。

对于带新集合元数据的记录，报告：

- 实际六题、十二候选，人工参考/人工变异及历史候选的来源边界。
- 每组正确判断、误拒、误放、有效覆盖、错误和缺失、重复波动、配对结果、用量；统计分母沿用现有规则。
- 明确仍为开发挑战集，不是 holdout 或真实缺陷集；相同候选的多次调用不等于新增独立任务。

保持旧 manifest 无新字段时的兼容读取与旧报告解释；不得改变旧实验分母、摘要或伪造新元数据。验证历史重建时在副本上执行，比较结果及原始证据哈希，不覆盖已有历史目录。

本轮用 FakeLLM 验证扩容后的调度、元数据隔离和报告数量，不进行真实调用。十二候选若未来仍采用两组各三次，计划数会是 72；**这只是数学推导，不代表本轮授权 72 次付费请求**。

## 9. 验收与失败处理

- 先在新临时目录记录现有非 live 基线结果与受保护文件哈希，显式使用 worktree 源码；不以激活虚拟环境代替导入路径核对。
- 先写失败测试，覆盖实际自定义 fixture 变化、相关 manifest/契约/验收变化、无关集合变化不误伤、旧报告兼容，以及十二候选的判别条件。
- 所有六个正例通过可见和新增隐藏验收，六个反例可见通过且隐藏真实断言失败；失败必须能对应到预先声明的机制。
- 验收文件缺失、标签不成立、未知候选、空集合、摘要不符、跳过/缺失测试、运行异常均拒绝 ready；保留现场并记录实际原因，不自动替换样本或削弱断言。
- FakeLLM 验证十二候选时的请求数量、两组只有说明不同、私有 canary 不出现在请求中、预算不足不初始化客户端、无自动重试/付费续跑。
- 报告能处理新集合，旧真实 36 次记录在副本上离线重建与原统计一致；旧原件哈希不变。
- 全量 non-live、相关 ruff、git diff --check 通过；确认原资产和历史结果未变。离线检查的“通过”只表示工程和标签校准，不称模型成绩。
- 按既有流程安排独立只读审查；发现重要问题先复现再修正。问题、证据、处理、验证、未解决项逐步追加日志。

如果发现新增判别点需要改公开业务契约、扩大生产代码范围、或必须引入额外依赖，则暂停该部分说明原因并重新确认，不将它藏进实施细节。
