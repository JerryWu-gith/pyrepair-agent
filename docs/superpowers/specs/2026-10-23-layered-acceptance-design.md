# 缺陷核心验收与上游扩展回归：计分修订设计

日期：2026-10-23。状态：用户在核对任务数与测试数后回复“好的继续吧”，批准具体范围；本轮离线实现与验收完成，尚无新模型性能结果。

前置：[公平工作流对照设计](2026-10-23-fair-workflow-comparison-design.md)。本修订仅解决 more-itertools 任务的验收范围与结果表达，不改变 Agent 主体，不修复或声称已定位上游整套运行时间波动的根因。

## 1. 已确认的选择与约束

采用 A：目标缺陷的核心验收与上游扩展回归分开执行、分开记录。另一选择是保持旧范围继续排查运行时间波动；不采用删除压力测试后仍声称原范围通过，也不提高原有 120 秒上限。

- 只做离线实施、Docker 校准与脚本化模拟；不读取 .env、不调用真实模型、不增加付费预算。
- 继续使用 evaluation-v2 托管隔离工作区；不提交、合并、推送或创建 PR，不修改 main。
- 旧任务、隐藏测试、参考/错误补丁、旧清单与全部失败/诊断目录只读保留；新口径另建 revision、清单和冻结包。
- 相同题目的两个方法使用相同核心与扩展验收、容器限制、顺序规则；在获得新模型结果前固定范围，不事后选测试。
- 本轮不修改 src/pyrepair，不改可信容器执行协议或 Docker 安全配置；只扩展评测装配、资产和测试。

## 2. 核对结果与术语纠正

more r1 运行 tests/test_more.py、tests/test_recipes.py、tests/test_pyrepair_repro.py。该选择不包含 unittest load_tests 注入的 doctest，因此本设计严格称为“上游扩展回归”，不是整个项目全部测试入口。

旧参考输入在相同环境中既出现约 10 秒通过，也出现约 115 秒通过与超过 120 秒超时。诊断提示可能与并发压力测试附近有关，但尚未证明单个节点、宿主负载或逻辑死锁是根因。分层验收是覆盖范围修订，不将旧超时改判为通过。

## 3. 新任务资产与核心范围

more 任务 ID 保持 os_more_seekable_1269，revision 从 1 增为 2。新建 benchmarks/manifest_opensource_v3.json：引用 more r2 与原样保留的 boltons r2；合成任务仍使用 manifest_synthetic_v3.json。题目总数仍为 18 合成＋2 开源，都是既有 dev，不增加“新真实任务”或 holdout 的宣称。

more r2 使用独立的 eval_cases/opensource_v2/os_more_seekable_1269 公共树。上游源码、原测试文件与 TASK 内容逐字节继承 r1，仅增加项目自编的公开测试选择桥接文件 tests/test_pyrepair_seekable_regression.py；不编辑、删除或跳过原有上游断言。私有资产继续引用原目录，gold.patch、wrong.patch、全部既有隐藏测试及其内容不变。

核心公开验收固定为：

1. tests/test_pyrepair_repro.py 的全部 3 个公开复现/默认缓存回归用例。
2. 桥接文件导出原 test_more 模块的 SeekableTest 与 SequenceViewTests 两个原始 unittest 类，不复制或重写测试方法。
3. SeekableTest 的 10 个自身方法及继承 PeekableMixinTests 的 4 个方法，共 14 个；SequenceViewTests 的 5 个方法。预期合计 19 个上游主测试节点。

选择理由：SeekableTest 直接覆盖被修复类的迭代、peek、bool、seek、索引及缓存行为；SequenceViewTests 覆盖 seekable.elements() 直接返回的 SequenceView。完整公共树仍保留其余上游测试，工具可以读取；“核心选择”不是隐藏或删除不相关源码。

核心私有验收仍运行原 hidden_tests/test_pyrepair_hidden.py 全部 4 个用例。F2P 的原 4 个节点不变；P2P 保留原 3 个节点并加入上述 19 个上游节点。正式计数以受控 Docker 实际 collection 核实，必须与预先声明的节点集合完全一致；数量不一致、未收集、skip、collection error 都不能冒充通过。

桥接仅负责选择现有测试类，不能修改其实现、pytest 标记或运行参数。若现有 pytest 模式不能可靠收集原始类，应停止并修订实现方案，不以手抄简化断言替代。

## 4. 上游扩展回归通道

为 more r2 在可信控制器侧保存一个版本化的扩展回归描述，明确原 r1 的 3 个文件、原 120 秒阶段上限、预期公开节点及选取理由。它的身份摘要进入新冻结包；它不包含隐藏测试，也不作为修复阶段额外反馈。

独立评分先在干净缺陷副本应用候选，执行原有规则检查和新版核心公开/隐藏验收。只有核心通过且候选可应用时，才在另一个干净副本应用同一份补丁，运行扩展回归；该副本不安装隐藏测试。核心失败、无补丁或规则拒绝时，扩展通道明确记为 not_run_core_failed / not_run_no_candidate，而不是通过或无记录。

扩展通道每份候选最多执行一次，不自动重试、补跑或提高上限。完整日志、实际收集节点、业务失败、超时、容器退出与清理证据分别保存。

- passed：选定文件正常收集、所需节点完整且全部通过，运行中资产未被修改。
- failed：正常执行后存在业务测试失败；不能称为可靠修复。只有参考版本对同一节点有通过证据时，才进一步称为“已确认补丁引入的回归”；其余标为扩展测试失败/归因未定。
- timeout：扩展验证未完成，不算通过、不改成业务失败，也不丢弃核心结果。
- environment_error / grader_error：基础设施或证据不可信，保留产物并暂停后续调度。
- not_run：没有适用候选、核心未通过、尚未调度或中断，必须附原因。

已确认清理正常的扩展业务失败或阶段超时不阻止后续计划槽位执行；这与核心评分器技术错误暂停的规则不同，必须在新协议中固定。OOM、清理失败、环境身份不符或容器证据矛盾仍按基础设施错误暂停，不能伪装成普通超时继续。

boltons 暂不扩大或缩小范围，仍是原先选定的 dictutils/urlutils 回归，不因此宣称其全库通过。没有配置扩展通道的题目记 not_applicable，不能填成 passed。

## 5. 校准与冻结要求

more r2 在同一受验环境下预先固定做 3 次独立核心校准，每次均复用 validate_case 的缺陷/参考/错误补丁验证；3 次必须全部 valid、无技术错误。此为事先规定的离线重复，不是失败后重跑直到通过。任何一次不符合则保留证据并停止该轮冻结。

核心校准要求：缺陷版本的 F2P 全失败、P2P 全通过；参考补丁的全部核心公开/隐藏测试通过；错误补丁通过公开阶段但被对应隐藏测试拦住。全部 19 个上游节点必须实际收集并处于 P2P，通过数量不能替代节点身份验证。

扩展校准固定执行缺陷版本与参考补丁各一次，保留完整状态。参考版本的正常业务失败、缺失节点、skip 或基础设施错误阻止冻结并要求调查；参考版本若只有已安全结束的 120 秒超时，则允许冻结核心任务，但扩展基准状态明确为 unverified_timeout，不宣称完整校准通过。原缺陷版本应至少含公开复现的预期失败。

实施审查补充：由未打补丁的可信缺陷基线实际收集完整扩展节点名单，固定到控制器冻结身份；参考版本及之后候选必须精确匹配整份名单，而非只满足 22 个关键节点。若缺陷基线自身超时、无法建立完整名单，则保留未知证据并停止冻结，不用残缺名单替代；只有参考版本超时可以在完整名单已建立的前提下标为未验证。该补充是缺失节点必须拒绝的保守实现，不增加任务、改变断言或放宽通过标准。

完成上述检查后，在全新目录准备 20 题包，仍对所有题目执行独立核心校准，不能使用旧成功产物填补新包。新 comparison 协议版本固定核心/扩展范围、节点和资产摘要、3 次 more 校准证据以及基线扩展证据。源码、环境、输入或任一通道身份改变都要求新包；旧包不自动迁移。

## 6. 持久化、恢复与报告

同一槽位保存三类独立产物：candidate.json、core-grade.json、extended-regression.json。核心评分完成立即持久化；扩展执行中断不能使核心结果丢失。journal 终态仅保存候选/评分摘要并绑定原始产物，避免 120 份大补丁或上游探针撑爆恢复日志。评分身份同时绑定候选补丁、任务指纹、验收范围及完整收集名单，恢复时也核对，不能只改内嵌布尔值或搬用另一补丁的成绩冒充成功。

恢复只读取已保存阶段并继续尚未开始的本地工作；已经执行但结果不完整的扩展阶段记 interrupted / unknown，不自动重跑。任何恢复都不能重新调用同槽位模型。新协议不把旧 grade.json 直接当作已具备双通道证据。

报告禁止裸写一个容易误解的“成功率”。至少分别给出：

- 核心验收通过率：核心通过数 / 全部计划方法运行数。技术错误、未运行仍在计划分母中，并分别列出，不只统计完成样本。
- 扩展回归状态：适用槽位的 passed / failed / timeout / error / not_run 数量，以及 not_applicable 数；分母和执行数量同时可见。
- 核心通过且扩展通过：只在配置扩展通道的适用范围内统计，不能把其他题目的 not_applicable 填为通过。
- Agent 内部成功但核心拒绝，以及核心通过但扩展失败/未完成，分别列出；保留逐题、逐 trial、两方法配对差异与分角色用量。

核心通过＋扩展超时的展示文案固定为“核心验收通过；上游扩展回归未完成”，不能称完整可靠修复。核心通过＋扩展业务失败展示为“目标缺陷验收通过；扩展回归失败”。核心通过＋扩展通过仅声称选定范围通过，不声称所有上游测试入口通过。

模拟报告仍明确 SIMULATION / NOT real model performance，所有真实性能比例未测量。最终 120 槽位 CLI 模拟只验证调度/持久化/报告，不冒充 120 次完整 FakeLLM 修复或真实模型结果。

## 7. 实施与验收边界

实施分为三个可独立核验部分：版本化资产与节点校准；双通道独立判分与中断恢复；冻结/报告/CLI 接入和实际离线收尾。先编写缺失功能的反例，再做最小实现；旧评分入口语义不变，新增行为只用于新版对照协议。

重点反例包括：原资产被改、少收集继承节点、隐藏资产进入公开输入、core_passed 被误报为完整通过、扩展超时被计为 passed、核心产物已保存后崩溃、终态与保存产物矛盾、扩展异常被自动重跑、两个方法验收条件不一致以及模拟输出出现真实分数。

实际验收包括 more r2 预定重复核心校准、独立扩展校准、新 20 题准备与 verify、最终 120 脚本槽位模拟、自编实际 Docker 双方法集成、相关回归与一次最终完整离线回归；核对生产源码及旧资产保护摘要，记录结果而非预填通过。原可信容器文件不变时仅核对现有合法环境，不隐式拉取镜像或重装依赖。
