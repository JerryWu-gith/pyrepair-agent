日期：2026-10-23。用户明确回复“好的开始吧”，批准A方案的离线实现。状态：实施中；不代表批准新增付费请求或发布。前置适配工程已完成，详见[适配验收报告](../../agent-docker-adapter-offline.md)。

实施检查点：已按[批准的分层修订](2026-10-23-layered-acceptance-design.md)实施comparison协议2，完成新20题核心校准、冻结身份核对与120槽位CLI脚本模拟；最终869项完整离线回归与1项显式Docker分层双方法验收通过。原协议1准备失败、more时延波动及大证据写入失败保留，不把新旧成绩混用。详见[离线报告](../../fair-workflow-comparison-offline.md)。

## 1. 要回答的问题

在同一批任务、相同初始公开证据和同一独立评分器下，完整PyRepair工作流相较单次生成补丁，修复表现、稳定性、耗时和用量有什么差异？

这是一项**整体工作流对照**，不是等算力实验，也不是某单一组件的因果消融。完整Agent可以继续查代码、测试、Review和重试，因而额外信息和消费本来就是被比较的能力；不能将差异单独归因于Agent Loop、Review或上下文检索。

## 2. 方案与推荐

| 方案 | 运行安排 | 取舍 |
| --- | --- | --- |
| A，推荐作为正式目标 | 两组均20题×3次：Agent60次＋single-shot60次＝120次方法运行 | 样本/重复次数对齐，可看逐题差异；费用较高，须另外批准预算 |
| B，缩小预先固定的配对子集 | 正式Agent仍依原标准20题×3次；仅固定子集做两组同次数比较 | 降低基线费用，但对照结论只适用于子集，不把子集分数当20题分数 |
| C，基线每题仅1次 | Agent60次＋single-shot20次＝80次方法运行 | 成本低但重复不对称，不推荐作为稳定性对照主结论 |

本阶段实现A所需的离线能力；**不执行120次真实运行**。最终收费安排在冻结后另行批准；若采用B，先更换清单、冻结新包，再启动，不能看完成绩后挑子集。60/120均为方法运行次数，不是API请求次数。

## 3. 两组究竟拿到什么、做什么

每题由可信控制器先在受验Docker环境跑公开基线，使用现有PytestParser与PublicContractContext构建一次初始公开证据包。包内包括：公开TASK、原始失败报告、仓库概览、当前选择的代码片段及相关路径。ContextBundle仍遵循现有16k字符/最多8片段策略；这不是宣称整个模型请求只有16k字符。初始运行只产生诊断，不加载模型。

```text
过滤后的缺陷公开副本 → Docker公开基线 → 公开失败报告＋ContextBundle（冻结）
                                         ├─ single-shot：一次模型响应 → 候选补丁
                                         └─ full-agent：工具/反馈/Review/重试 → 候选补丁
两组候选 → 各自干净缺陷副本 → 同一Policy及独立公开/隐藏验收 → 配对报告
```

| 条件 | single-shot | full-agent |
| --- | --- | --- |
| 题目、模型ID/端点、思考设置 | 相同并冻结 | 相同并冻结 |
| 第一次可见的任务/失败/代码证据 | 同一冻结包，不额外拼全部源码 | 同一冻结包；后续可通过既有工具获取新证据 |
| 指令与输出格式 | 单独固定提示词，只输出一份普通unified diff | 保持既有修复提示词、工具schema与完成规则 |
| 工具与反馈 | 无工具、无后续测试反馈、无格式修复追问 | 既有8工具调用/attempt、最多3attempt、每attempt最多11模型轮及独立Review |
| 补丁处理 | 严格解析/应用，失败不重问 | 原有流程生成候选 |
| 共同最终验收 | 同一源码允许清单、补丁规则、公开/隐藏测试和Docker环境 | 同左；Agent内部通过不替代独立验收 |

“相同初始材料”不等于“完全相同提示词/工具schema”。现有RepairAgent系统提示词要求只能通过工具修改，不能原封不动拿去要求single-shot直接输出diff；两套指令各自冻结并公开差异。single-shot没有LLM Review，这是整体工作流差异，不悄悄额外赠送第二次模型机会。

解析允许的外层格式必须在实现前固定：仅接受原始普通unified diff，或唯一一个标记为diff/patch的围栏且围栏外为空白。其余说明文字、多个围栏、tool_calls、空补丁、截断/无法应用补丁均记录对应失败，不能人工修补或自动追问。应用后使用既有apply_patch_checked与PatchPolicyGate，不执行模型提供的命令。

## 4. 冻结包与接口边界

新增独立comparison协议，不覆盖旧experiment protocol2、旧清单或旧54/54。复用已有安全资产、适配器与判分，不复制另一套隐藏评分逻辑。新增能力放在benchmarks/evaluation及测试；本轮不改生产src。

冻结身份至少覆盖：

- manifest_synthetic_v3的18题＋manifest_opensource_v2的2题；逐题revision、来源/split、指纹；合成与真实分组报告。
- 每题经过过滤的公开副本/公开执行描述、初始失败报告/ContextBundle及其摘要；所选失败node必须来自真实公开基线，不能从隐藏F2P或gold挑选。
- 初始失败报告的规范化规则：排除计时和暂存绝对目录等运行噪声；保留node、异常、业务断言和源码内容。不得随意删除数字或字符串来让不一致证据“匹配”。
- 实测补充：标准库绝对栈路径仍保留在traceback原文，但不作为仓库关联文件/工具目标；捕获与冻结重放使用同一元数据规则，日期和金额字面量不变。
- 两组固定提示词、full-agent schema和预算/超时、模型显式参数；未固定的提供方默认值明确记录，不能声称确定性复现。
- 全部相关运行源码摘要、Python/依赖身份、受验环境锁/镜像/可信harness摘要、独立验收身份。
- 确定的trial列表、两组执行顺序、额度策略和报告口径；顺序按预先固定的配对交替表执行，不根据已见结果换序。

新包统一选择现有受验Docker后端执行两类任务；旧synthetic默认入口保持不变。若某题与现有镜像不兼容，记录预检失败并停止冻结，不临时安装依赖或退回宿主，不自动剔题。

控制器持有私有验收指纹与题目对象；模型worker只接收公开描述和公开初始证据，不能拿到完整manifest、隐藏目录/节点、gold/wrong或私有验证清单。公开包和控制器验收身份分开存放。任何源码、公开材料、隐藏验收或配置摘要变化均拒绝续跑，须创建新包；旧产物只读保留。

full-agent在新评测装配中复用冻结公开失败/上下文，不修改生产RepairAgent。运行开始仍用Docker检查当前缺陷公开基线与冻结证据相符，之后交给既有流程；不能将冻结的旧“通过”证据冒充新执行。实现优先评测侧parser/context wrapper及校验，必要性不清的生产重构不包含在本轮。

## 5. 调用、预算、错误和恢复

源码核对：DeepSeekClient默认额外重试2次，SDK本身max_retries=0；现有响应台账只统计ModelClient调用，并不测量客户端内部HTTP重试。新对照在**评测装配侧**将额外重试设0、记录该设置；普通CLI不变。所有角色共享本次运行的调用额度守卫，模型调用前原子持久化预留，进程中断也不归还已预留额度。

- single-shot每次最多1个模型调用；full-agent保留原有循环上限，另受冻结的逐次/全局调用上限约束。
- 后续真实预算必须单独批准；这次只用FakeLLM或自编安全夹具验证，不读取.env或消耗旧授权。若未来加入传输计数器，分别保留调用预留数、实际发起数、响应数与失败/未知用量，不能全部叫“成功请求”。
- 不确定用量不能写0；token与已核实价格/费用另列，没有提供方价格和完整用量证据就不声称精确人民币费用或硬费用上限。
- 正常未修复/补丁格式或应用失败为方法结果，记录后按冻结顺序继续；API错误、提供方响应协议损坏及执行基础设施错误则保存证据并暂停后续调度。两者都不选择性补跑。正式表保留计划槽位、未运行和技术错误，不能只统计成功返回的样本。
- 追加式journal按(case,trial,method)记录started/response/candidate/grade/terminal等阶段。响应和候选完成即落盘；恢复只能继续未完成的本地处理/判分，不能自动再花一次API来填同一槽位。确需新执行时另批准并保留旧耗费。

本阶段CLI只提供prepare/verify/simulate或等价离线命令；真实开源模型入口保持拒绝，不提前增设可直接消费API的旁路。预算确认阶段再对真实执行入口做单独审查和启用。

## 6. 报告与离线完成标准

主结果按“全部计划trial的独立验收通过比例”分组，另外保留Agent内部状态；不能要求single-shot伪造Agent的success，也不能把Agent内部success当独立通过。单独报告Agent声称成功但验收拒绝、仅形式/策略拒绝、普通测试失败、基础设施错误与未运行。输出逐题3次结果、同题两组配对差异、耗时及分角色已知用量；只有3次重复，不夸大统计稳定性。

离线完成要求：

1. 相同公开初始输入的摘要/内容对齐、模型输入无隐藏资产；篡改身份/输入/环境即拒绝，且拒绝发生于任何模型构造/调用之前。
2. single-shot只有一次调用，正确补丁通过、错误/越界/不可应用/工具调用式响应失败；无格式修复追问，无宿主执行上游代码。
3. FakeLLM贯穿完整小任务的两个方法和独立评分；调度模拟覆盖20题×3次×2组的120槽位，明确是模拟，不生成真实模型成绩。
4. 配额竞争/中断、响应后崩溃、判分中断、恢复、未知用量与历史保留均有反例测试；Docker不可用时停止而非回退。
5. 受控Docker新入口做限定实际离线检查；可信容器文件如改变则必须重建/重验，否则核对并复用现有合法锁，不能伪称每次都重新准备。
6. 一次集中验证与限定差异审查、更新工程日志/README/检查表；默认CLI/旧experiment/旧成绩不受影响。不自动提交、合并、推送或PR。

## 7. 自审结论与下一步

本设计仅覆盖公平基线与离线冻结/模拟能力；付费运行和最终性能结论不在本次实施范围。已检查次数口径（120方法运行≠120请求）、公开/私有边界、两种提示词差异、无自动重试/补跑、阶段恢复与旧协议兼容，没有用待测性能数充当成果。

已获用户批准，使用writing-plans制定小步TDD实施计划，按用户偏好Inline推进。A为正式目标而非此次消费授权；如预算后续不足，正式启动前另冻配对子集，不事后挑题。
