“一起处理”指统一建设与正式批次，不要求把三十个源码目录同时读入内存，或同时启动三百个模型运行。准备和执行均可按受控批次推进，但在全部题集冻结前不启动任何新正式模型槽位。

## 2. Gold set 的交付定义

本项目的 gold set 是经过校准的任务与行为验收集合，不是只有 `gold.patch` 的文件夹，也不是把网上的问题链接凑够数量。每道正式任务必须绑定：

- 不重复的 case ID、修订号、来源类型及开发/验收用途标签。
- 固定缺陷源码、公开任务说明、公开失败复现，以及逐项登记的覆盖层。
- 隐藏行为测试、原有行为回归范围、已收集的 F2P/P2P 节点和明确的跳过规则。
- 可使任务通过的参考源码补丁，及用于暴露验收薄弱点的人工不完整补丁。
- 固定运行环境、超时、允许编辑范围、许可和输入摘要。
- 可追溯的基线、参考修复、不完整修复三类离线校准结果。

参考补丁不是唯一正确输出。独立评分依据公开行为合同及测试结果，而不是候选补丁与参考补丁的文本相似度。题目因环境无法运行、测试漏收集或参考修复本身错误而不合格时，不能记作 Agent 失败来完成数量目标。

## 3. 统一管理，不混淆来源和用途

推荐统一清单、保留分组的方案：一次实验管理五十题，报告同时展示自建二十题、开源三十题及更细的开发/验收分组。

不采用完全混成一个不带来源的五十题分数：题型和暴露程度不同，会掩盖真实缺陷表现。不采用另建三十道全新开源题再加旧二题：用户要求累计三十题，额外扩成三十二题没有必要。

现有二十题都已用于本项目开发，保持 `split=dev`。新增两道自建题也作为自建能力开发任务。新增二十八道真实题只有在未用于 Agent 提示词、工具或决策策略调优时才可保持 `split=holdout`；若用于调优，必须记录并改标，不能再宣称这二十八题全部未用于开发。

所以最终三十道开源题是两个已知开发题加二十八个新增任务，不称为三十道全部未见任务。这里的 holdout 仅是对本项目调优过程的隔离，不证明基础模型训练时未见过公开历史缺陷。

统一清单可以引用原有资产目录，不需要复制、移动或重写全部任务文件。修订号不同不是新题；同一缺陷的多个复现、断言和重复运行也不是新题。真正改变任务合同或隐藏验收时使用新 revision 和新资产路径，旧资产和旧成绩保留。

## 4. 三十道真实任务的选题规则

至少覆盖五个独立上游仓库。现有两题来自 more-itertools 和 boltons；已核对的五个候选来自 Click、python-dotenv 和 packaging。即使使用这五个仓库，也不能只因数量达标而把绝大多数新增题集中在同一种行为错误上。

覆盖字符串或配置解析、集合/迭代器状态、参数语义、跨函数或跨文件一致性、序列化与反序列化等不同故障。明确记录生产修改文件数和参考修复大小；小补丁真实缺陷不包装成大型复杂工程任务。

每道题核对真实 Issue 或 PR、已合并生产修复、第一父缺陷版本、许可证和文件字节。候选列表及排除原因在正式模型结果产生前固定。不能因模型失败换题，也不能把参考补丁揭示的具体修复步骤复制到公开任务说明。

已有 [五题来源记录](../../external-pilot5-candidates.md) 作为本批候选子集，不等同于五题已验收。若离线预检不合格，记录环境、合同或参考修复的证据及替换理由，再在模型运行前冻结最终清单。

## 5. 冻结 Agent，改动集中在评测侧

生产 Agent 以 `7c9508e63ff3a133e7599b3a2ca439e935f10295` 中的 `src/pyrepair/`、`pyproject.toml` 及方法配置为冻结依据。当前文档提交不改变该被测代码。正式执行前重新记录实际源码、提示词、工具 schema、评测适配器、配置和环境摘要。

不为题目调整修复或 Review 提示词、上下文预算、工具语义、Policy Gate、重试策略或完成条件。若后续必须改变 Agent，另立被测版本和实验，不把前后结果拼成同一冻结版本。

现有正式入口绑定固定二十题，来源登记也绑定旧两题，不能只在旧 manifest 加 ID 后启动五十题。新增统一题集的显式准备、校准、检查、执行入口，复用现有 worker、paired slots、journal、独立评分和进程监督。旧二十题入口和旧实验身份保持原约束。

新开源任务的公开编辑范围按整个生产包的现有 `.py` 文件登记，不按参考补丁涉及文件缩窄；仍禁止修改测试、配置、依赖或环境。已有任务如维持原编辑范围，须保留并披露；若拓宽或改变合同，创建任务新修订，不覆盖历史资产。两种方法及 Review 接收相同的该题公开范围。

## 6. 来源、公开输入和执行环境

上游源码先作为数据归档读取，核对 Git tree 和逐文件 blob；不在宿主导入源码、执行测试或运行上游构建钩子。保留固定版本的项目布局及许可；公开运行副本不包含 Git 历史、修复提交、参考补丁、隐藏测试或评分控制目录。

公开任务、失败报告和上下文只描述待修行为，不包含上游 PR 的 root cause/fix 解释。可信侧持有模型密钥，源码和测试执行放在无密钥、禁网的 Docker 侧。候选冻结后才做隐藏验收，评分结果不回流生成流程。

先审查现有 Python 3.13 固定镜像与每个仓库的兼容性。`src/` 布局须由可信评测协议明确绑定导入根，并验证实际加载的是候选源码而非环境中同名库。不能为了兼容而修改缺陷生产代码。

需要不同依赖或 Python 环境的任务，可以使用按仓库或任务绑定的新环境锁；不能假设一个镜像适合所有三十题。依赖和镜像标识固定，测试阶段不联网安装。新增导入根或环境协议须同步校验、容器入口、摘要及定向测试，旧环境锁不就地改写。

## 7. 离线验收与分组完成门槛

逐题满足：缺陷基线的声明 F2P 节点失败而 P2P 节点通过；参考生产修复通过全部核心节点；人工不完整补丁通过公开复现而被至少一个合理隐藏边界拒绝。未导入、未收集、环境错误或不当跳过不能冒充行为测试结果。

测试期望来自公开行为合同和可信上游依据，不追加无说明的新业务要求。扩展回归事先声明执行范围、节点与跳过原因；局部回归不写成全仓全量。随机或平台相关测试须先暴露并处理稳定性问题，不根据模型候选成败调整验收。

旧任务可以复用完全同一源码、测试、协议和环境摘要下的有效校准证据；身份变化则重新校准。不能只因旧模型曾通过就认定评分资产正确。新增两道自建任务依据建设阶段发现的覆盖缺口选择，不根据新一轮模型成绩定制容易题凑数。

全部五十题通过离线验收、没有未解决的环境或任务合同问题后，冻结唯一正式清单和逐槽运行顺序。离线 FakeLLM 验证只证明接线，不写成模型性能。定向测试和必要集成检查完成后进入下一步，不为每项文档或资产变更重复整套历史长测试。

## 8. 统一 DeepSeek 正式评测

固定模型 `deepseek-flash`，沿用当前 thinking/reasoning 配置及两种方法：single-shot 每槽一次补丁生成；full-agent 每槽最多三次内部修复、每次八次工具调用、最多十一轮模型响应及独立 Review。不同方法不是等调用量或等算力设置。

正式规模为五十题乘两方法乘三次独立重复，共三百个方法运行；每方法一百五十次。它们不是三百次 API 请求，也不是三百道独立题。

每个独立运行重新创建 worker、模型客户端、工作区和运行状态，不继承上一遍对话、补丁、结构化反馈或隐藏评分。同一 full-agent 运行内部仍按现有机制传递跨 attempt 的结构化反馈。预定次数全部计入统计，不只补跑失败题，不取最好的一遍冒充平均表现。

用户不要求以 DeepSeek 费用缩减题数或重复次数。保留用量记录、超时、异常停止及有限实验身份。按现有每槽上限，整个正式批次最多 5,550 次模型调用预留（150 个 single-shot × 1，加 150 个 full-agent × 36）；不是费用预测、HTTP 请求数承诺或必须用完的额度。

API 响应解析、运行协议或环境的技术错误停止并记录，不自动技术重试。无效补丁、Policy/Review 拒绝、测试不通过等普通方法失败依现有规则保留并继续后续槽位。断点恢复只执行未开始且身份匹配的槽位，已发起但状态不明的请求不能静默再跑。

## 9. 成绩口径与发布边界

所有三百个预定结果来自新的冻结实验，不能拿旧二十题的 59/60、36/60 与新增任务结果拼成一轮新成绩。旧结果完整保留，作为历史实验单独引用。

正式报告分别列出自建二十题、开源三十题，以及开源中已有两题与新增二十八题的结果。可以提供五十题整体汇总，但必须与分组指标同时展示，明确它不是五十道全未见任务。

每组报告核心验收成功率、每题 0/3 至 3/3、三次全部通过的任务数、失败类型、调用和 token 用量、方法耗时及独立评分耗时。三次重复等权计入，不把它们当成新的缺陷种类或足够强的统计显著性证据。

完成题集建设不等于完成性能评测。阶段性交付分别明确：来源候选、资产已准备、离线已验收、实验已冻结、真实评测完成。保留问题和解决记录，不提前更新 README/简历为已实现成绩，不自动推送或创建 PR。
