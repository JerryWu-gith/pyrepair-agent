# PyRepair Evaluation v2：独立验收与可复现评测设计

日期：2026-10-14

状态：用户已于 2026-10-14 确认本设计；第一阶段于 2026-10-15 完成实现及离线验证，尚未产生新版模型评测成绩。结果见 `docs/evaluation-v2-verification.md`。

源码基线：`8bf2fab`。本文不是评测成绩报告。

## 1. 目标与实施边界

让评测能够区分“修复流程认为成功”和“补丁确实通过独立验收”，保留每次运行的证据，支持稳定性分析，并为真实开源缺陷与消融实验建立基础。

采用分阶段交付，而不是同时重写 Agent、引入容器平台并扩充大量任务：

| 阶段 | 交付内容 | 验收边界 |
| --- | --- | --- |
| 第一阶段：评测内核 | 独立 grader、隐藏验收、参考修复预检、重复运行、严格续跑、证据持久化；原有 15 题的 v2 验收包及 3 个多文件试点 | 本文详细约定；先做不调用 LLM 的自动验证 |
| 第二阶段：真实任务 | 筛选真实 Python 开源缺陷，固定仓库提交、依赖与来源，接入任务环境；优先试点 3 题，通过后再扩展 | 单独设计环境适配与容器执行；不能把人工样例标为真实缺陷 |
| 第三阶段：效果归因 | 完整版、无初始上下文增强、无跨 attempt 结构化反馈的同条件对比；扩充多文件与真实任务集 | 独立验收和重复运行稳定后，再增加最小配置接口 |

总体希望扩展到约 10 个多文件任务、10 个真实缺陷；数量是目标，不是第一阶段的交付声明。选题必须按预先声明的兼容范围，不按模型是否修成功事后筛题。

第一阶段不修改 `coordinator.py` / `repair_agent.py` 的双层循环，不放宽 Policy Gate，不修改现有修复 CLI 的默认行为。不接入 MCP，不重做通用沙盒，不自动 Push，不自动启动付费评测。保留工作区中既有的 PDF、Word、面试脚本及源码学习注释。

## 2. 已核实的现状

- `benchmarks/run_benchmark.py` 的最终状态来自 `report.json["status"]`，目前没有补丁外部验收。
- `latest_case_records()` 按 `case_id` 归并；重复运行不能直接复用这个汇总规则。
- 旧 `--resume` 会重试技术错误并以最后结果汇总；v2 不沿用这一统计口径。
- 每题使用临时目录；当前返回聚合记录后目录被清理，完整轨迹和日志没有作为独立文件长期保存。
- 原有 15 题是小型人工缺陷任务；缺少多文件能力集与隐藏测试。
- `fix.patch` 只在现有修复流程接受补丁时写入有效内容。没有导出的补丁时，v2 按“未提交候选补丁”记录，不窥取内层尚未接受的工作区改动。
- `TestRunner` 使用 `sys.executable`，真实任务的不同 Python/依赖环境不能仅靠更换仓库路径解决。
- 当前策略限制最多 3 个修改文件、80 行增删，只接受 Python 源文件；本次不为提高分数而调整这些约束。

## 3. 方案选择

| 方案 | 优点 | 问题 | 决定 |
| --- | --- | --- | --- |
| 只增加样例 | 快、主流程不变 | 无法发现可见测试不足导致的误报，缺少独立证据 | 不采用 |
| 新建 v2 评测入口，沿用现有修复引擎 | 保护旧结果与已有命令，能够分阶段验证 | 增加少量评测模块 | 采用 |
| 立即全量接入 SWE-bench / 容器平台 | 接近大型开源项目评测流程 | Issue 输入与 pytest 输入不同，依赖和预算跨度大，不利于先验证评分正确性 | 后续按范围接入 |

旧 `benchmarks/run_benchmark.py`、旧 manifest、旧报告和原始 JSONL 保留。v2 使用新入口和独立结果目录，不把旧 15/15 改写成隐藏验收成绩。

## 4. 数据流与独立性

一次 trial 的顺序固定为：

1. 验证任务、参考修复和运行环境；预检不通过的任务不可冒充模型失败或成功。
2. 从固定的 buggy 模板创建 Agent 输入副本，只包含源码、可见测试、运行配置和公开任务说明。
3. 用原有修复引擎运行一次完整任务，最多 3 个 attempt；不把隐藏测试、参考补丁或评测元数据加入模型消息。
4. 在临时目录清理前，保存修复报告、轨迹、pytest 日志和导出的候选补丁。
5. 从同一 buggy 模板另建全新验收副本，不复制 Agent 的工作目录、缓存或新增文件。
6. 验证补丁路径与变更范围，应用导出的补丁，再安装评测方持有的隐藏测试。
7. 执行明确列出的可见测试、隐藏测试及回归测试，生成独立 `grade.json`。
8. 持久化 trial 终态，更新实验报告。隐藏失败原因仅进入评测产物，不反馈给本次或下一次 trial 的 Agent。

评测器负责运行流程、断言验收及结果汇总；现有 Agent 仍负责诊断与生成候选补丁。最终验收不调用第二个 LLM 来替代 pytest 判分。

### 隐藏测试的准确边界

第一阶段隐藏资产位于 Agent 输入树之外；工具路径校验和上下文索引不会接触这些资产。隐藏指“对本次 Agent 工具与提示词不可见”，不等于公开模型从未见过题目。

本地副本不是操作系统安全沙盒。pytest 会执行 Python 代码，同一用户身份下的恶意代码仍可能访问宿主资源。第一阶段仅运行审核过的自建任务，不宣称抵抗恶意补丁。真实仓库和不可信代码执行应在第二阶段通过容器隔离设计解决，不能把目录分开写成强安全保证。

## 5. 任务格式与 gold set

使用 `benchmarks/manifest_v2.json` 描述任务，评测端加载为有类型的数据对象；不把这个文件直接交给 Agent。

每题包含：

| 字段 | 含义 |
| --- | --- |
| `id` / `revision` | 稳定任务编号与任务版本 |
| `suite` / `split` | `regression` 或 `capability`；`dev` 或 `holdout` |
| `source_kind` / `origin` | 人工或真实缺陷；来源、许可、固定提交等信息 |
| `buggy_path` | 原始缺陷源码及可见测试目录 |
| `public_description_path` | 公开功能约定；准备输入副本时作为 `TASK.md` 复制进去 |
| `private_path` | 评测端的隐藏测试、参考补丁和错误补丁；不得进入 Agent 输入副本 |
| `visible_tests` / `hidden_tests` | 明确的 pytest 相对路径列表，不能从空目录“通过” |
| `fail_to_pass` | 在 buggy 版本真实失败、在参考修复后通过的 node id |
| `pass_to_pass` | buggy 版本原本通过、候选修复后必须保持通过的 node id |
| `allowed_source_paths` | 可修改的业务源码集合；不包括测试、配置或私有资产 |
| `timeout_seconds` | 预检和验收的超时限制 |

例如页码题的任务合同会明确：页码从 1 开始，合法区间为 `1 <= page <= total_pages`。可见测试复现上界缺陷；隐藏测试检查下界、越界及不同总页数，不能靠没有公开的业务要求判错。

gold set 不是一份答案字符串表，而是一批经过预检的任务包：

- buggy 版本必须复现指定失败；不存在依赖缺失、收集错误或全部跳过冒充缺陷。
- 参考补丁应用后，全部指定验收测试必须通过。
- `pass_to_pass` 在修复前真实通过，修复后仍通过。
- 至少一个有针对性的错误补丁必须被隐藏测试拒绝。例如页码题的 `return True` 能过可见测试，但不能通过隐藏测试。
- 接受行为正确的不同实现，不比较候选补丁是否与参考补丁逐字相同。
- 记录实际采集到的 node id，要求指定测试确实执行且通过；必需测试被 skip / xfail 不能当作通过。

预检结果与源码、任务说明、隐藏测试、参考补丁、评测器和环境指纹绑定。任一输入改变都使旧预检失效。

## 6. 第一阶段任务集

### 原有 15 题

保持旧题源码和可见测试不变，在独立 v2 资产中补充公开合同、隐藏测试、参考补丁与错误补丁。v2 因输入说明和验收不同，单独报告，不与旧成绩直接比较。

这些题全部标记为 `regression/dev`，不能重新包装成未见过的最终测试集。

### 3 个多文件试点

新增 3 个自建 `capability/dev` 任务，明确标记人工来源：

1. 订单金额与折扣：服务入口、折扣规则与金额计算分层，验证多商品、边界金额与默认折扣行为。
2. 库存预留与取消：服务层与库存状态模块协作，验证连续调用、取消恢复及非法操作不污染状态。
3. 日期时间转换与输出：解析、标准化和序列化分层，验证带偏移时间和边界日期的一致性。

每个任务必须要求跨文件理解，至少两个试点的参考修复涉及两个业务模块；只增加无关文件不算多文件任务。不得超过当前文件/行数约束。具体业务合同、代码与测试在实施计划中逐题落地。

首批任务用于验证评测工程，暂不声称拥有真正冻结的 holdout。第二阶段按来源仓库或缺陷家族划分开发与最终集合；最终集冻结后，不用其结果反复调整提示词再报告为未见题成绩。

## 7. 补丁应用与验收规则

第一阶段仅支持现有业务 Python 文本文件的 unified diff，不支持文件重命名、二进制、子模块、符号链接、文件模式更改或测试/配置修改。不能安全解释的补丁应拒绝，不进行模糊匹配或自动修补。

- 在应用前校验路径；拒绝绝对路径、Windows 盘符/UNC、`..`、跨目录链接及非白名单文件。
- 在新建且边界已验证的验收目录中调用 Git 的补丁检查/应用，使用参数数组和 `shell=False`；不使用 `--unsafe-paths`。
- 应用前后对业务文件构建快照，复用 `PatchPolicyGate` 做规则检查，防止直接提交补丁绕过现有约束。
- 未通过路径/策略检查的补丁不能进入 pytest。
- 可见与隐藏测试分阶段执行并保存日志；列出的必需测试缺失、未采集或被跳过都不能算通过。
- 显式固定验收 pytest 的 rootdir 为当前验收副本，避免临时目录位于父项目内时继承父项目根目录，生成不能在当前副本重放的 node id。预检与正式验收使用一致的 rootdir 和配置选择规则。
- 验收前后核对测试与评测配置的哈希；发现变动记为拒绝，不接受候选代码篡改验收资产。
- 验收子进程不需要 LLM Key，使用明确筛选的环境变量，不传递 API Key；日志不记录完整环境。
- 子进程超时必须终止并清理；超时不等于测试通过。

上述措施用于控制错误与非恶意取巧，不把本地模式提升为强隔离执行器。

### 独立结果

保留 `agent_status` 和 `grade_status` 两套字段，不覆盖修复引擎原始状态。

| `grade_status` | 含义 |
| --- | --- |
| `passed` | 补丁合法，全部指定验收测试执行且通过 |
| `no_patch` | 没有导出的有效候选补丁 |
| `patch_rejected` | 不支持的格式、越界/受保护路径、策略违规或不能应用 |
| `visible_failed` | 候选补丁未通过可见测试 |
| `hidden_failed` | 可见通过，隐藏验收未通过 |
| `timeout` | 已预检的任务在候选验收时超时 |
| `environment_error` | 环境创建、解释器启动等基础设施故障 |
| `grader_error` | 无法可信判分，如结果文件损坏或评测器内部异常 |
| `not_run` | Agent/API 运行异常，没有进入验收 |

任务预检失败独立记录为 `invalid_task`，不进入模型运行。预检通过后，候选改动导致的导入/收集错误记为对应测试阶段失败，不转移成环境故障。

总体成功条件是 `agent_status == success` 且 `grade_status == passed`。若修复引擎异常地报告非成功却导出了可验收补丁，保留该不一致信息，不偷偷算总体成功。

## 8. 重复运行、续跑与统计

### 实验身份

每次实验固定 `experiment_id`、`protocol_version=2`、任务及资产哈希、源码提交/源码树哈希、模型和非敏感 API 配置、预算、Python/依赖版本、随机性设置（含使用服务默认值的情况）。包含工作区源码变化时必须体现在指纹中。

每个 trial 用 `(experiment_id, case_id, trial_index)` 唯一标识，`trial_index` 从 1 开始。每次从固定模板、空消息历史和干净工作目录启动，不复用前一个 trial 的反馈或缓存。

第一阶段默认 `--trials 1`，建议正式测稳定性时显式使用 `--trials 3`。每个 trial 内仍保持现有最多 3 个 attempt、每个 attempt 最多 8 个工具调用；扩大预算属于新的实验配置，不能混算。

### 续跑规则

- 先保存完整预定任务网格及实验配置，再执行 trial。
- `--resume` 只补未启动或中断的 trial，不重跑已结束的失败/错误来替换成绩。
- 中断记录保留；若已有完整补丁和修复报告，优先恢复验收，不重新请求模型。若无法恢复，重新启动同一逻辑 trial 时记录递增 `execution_index` 及已有部分成本，不能抹去中断。
- 所有原始执行记录保留；正式报告明确显示中断/恢复次数。
- 模型、预算、任务集合、任务内容、协议或环境指纹不一致时拒绝续跑。
- v1 JSONL 不能作为 v2 的 `--resume` 输入；旧入口仍负责读取旧数据。
- 已结束任务如需重跑，建立新实验并与旧实验并列展示。

### 指标口径

设计划 trial 总数为 N，已终结为 C，独立验收总体成功为 S：

- 完成度：C / N；有 pending 时报告必须标注“未完成实验”。
- 当前完成部分通过率：S / C，C 为 0 时显示 N/A；最终正式通过率为 S / N，仅在全部完成时称最终成绩。
- 错误、超时、无补丁计入终结次数且不是成功，不从分母静默删除。
- 稳定解决题数：全部指定 trial 已结束且均成功的题数；没有跑齐的题不得算稳定通过。
- 首 attempt 独立通过率：总体成功且 `attempt_count == 1` 的 trial 占比。不是“第一个 trial 成功率”。
- 误报数：`agent_status == success` 但独立结果是可判定的失败；基础设施/评测器错误另列“未能验收”，不自动断言补丁错误。
- 分别展示 Agent 耗时、grader 耗时、工具调用、模型调用、输入/输出 Token、失败类别和题目类别。
- 未采集到成本的记录标为未知，不冒充 0；区分 Repair 和 Review 的 Token 覆盖范围。
- `invalid_task` 不进入已预检任务的模型分母，但报告必须同时列出原始候选任务数、排除数和逐题原因。
- 不报告大规模泛化结论，不将 3 次全部成功说成数学上保证稳定；不只选每题最好的一次。

## 9. 文件边界、命令与产物

新增评测目录，模块只承担单一职责：

| 文件/目录 | 职责 |
| --- | --- |
| `benchmarks/run_evaluation.py` | v2 命令入口，不改现有修复 CLI |
| `benchmarks/evaluation/cases.py` | 任务数据结构、manifest 校验、输入准备和内容指纹 |
| `benchmarks/evaluation/grading.py` | 任务预检、补丁应用、独立测试与验收结果 |
| `benchmarks/evaluation/experiment.py` | trial 调度、续跑规则、调用现有修复引擎、原始证据保存 |
| `benchmarks/evaluation/reporting.py` | 指标计算与 Markdown 报告，不执行测试或调用模型 |
| `benchmarks/manifest_v2.json` | 任务版本和集合声明 |
| `benchmarks/eval_cases/` | 多文件任务的公开输入 |
| `benchmarks/eval_private/` | 全部 v2 任务的隐藏测试、参考补丁与错误补丁；只对评测器开放，不代表 Git 仓库私密 |
| `tests/test_evaluation_*.py` | 无付费模型调用的自动化验收 |

预计命令接口：

```powershell
# 验证任务和参考修复；不调用模型
.\.venv\Scripts\python.exe benchmarks\run_evaluation.py validate

# 单题独立补丁验收；不调用模型
.\.venv\Scripts\python.exe benchmarks\run_evaluation.py grade --case case_04 --patch <补丁路径>

# 显式启动付费模型运行；实施时不会自动执行此命令
.\.venv\Scripts\python.exe benchmarks\run_evaluation.py run --case case_04 --trials 3 --model deepseek-v4-flash

# 补齐已有实验未完成的 trial，配置必须一致
.\.venv\Scripts\python.exe benchmarks\run_evaluation.py run --resume <实验目录>

# 从已有记录生成报告；不调用模型
.\.venv\Scripts\python.exe benchmarks\run_evaluation.py report --experiment <实验目录>
```

`grade` 是单补丁诊断，不伪装成一条正式模型实验；`validate` / `grade` / `report` 不要求 API Key。所有上述接口在本文确认时仍为设计，不可当作已实现命令。

新结果写入 `benchmarks/results/v2/<experiment_id>/`，保留：

- `experiment.json`：配置、指纹和预定 trial 网格；不含密钥。
- `trials.jsonl`：追加式事件及终态，重启后不覆盖失败历史。
- `report.md`：本次实验结果；不覆盖 `docs/benchmark-results.md` 的历史成绩。
- `<case_id>/trial-<n>/execution-<n>/agent/`：`report.json`、`trace.jsonl`、`pytest.log`、`fix.patch`。
- 对应的 `grader/`：补丁应用日志、可见/隐藏测试日志、结构化测试结果、`grade.json`。
- `validation/`：逐题预检证据和不合格原因。

运行目录由带随机后缀的 ID 创建，使用防冲突创建方式。验证和单补丁诊断使用独立产物目录。清理只针对本次创建且已验证路径的临时副本，绝不删除原题、参考资产或实验结果。

更新 `.gitignore` 忽略 v2 自动生成的大型结果目录；不删除已跟踪的历史结果。README 增加 v2 使用说明和协议局限，但在新 live 数据产生前不填写新成功率或覆盖率。

## 10. 自动验收与实施顺序

先用确定性补丁与 fake model 验证评测器，而不是先花费 API 费用：

1. 正确参考补丁通过，可见测试取巧补丁被隐藏测试拒绝。
2. 未修复版本失败；必需测试空收集、skip / xfail、缺失 node id 不能通过。
3. 多文件补丁可以合法应用；越界、测试篡改、非白名单文件、符号链接与格式错误被拒绝。
4. Agent 输入副本中没有参考补丁、隐藏测试、评测元数据或旧运行产物。
5. 验收副本来自固定模板，不能继承 Agent 偷写的测试或缓存。
6. 3 次独立 trial 均被保留，attempt 与 trial 统计不混淆。
7. 续跑跳过全部已终结结果，包括失败和技术错误；配置变化拒绝续跑。
8. 中断后证据可恢复且历史不被覆盖；缺少产物不能判成功。
9. 预检失败、模型错误、补丁失败、隐藏失败和验收基础设施错误能区分。
10. 统计用人工构造的小记录集合验证分母、误报数、稳定解决题数及未知成本。
11. 15 个原有任务的 v2 参考修复与 3 个多文件试点全部完成离线预检。
12. 现有离线测试、原 benchmark 命令与新测试通过；新版故意失败的 fixture 不被根 pytest 自动收集。

实现顺序：评分核心与代表性任务 → 证据持久化与 trial 调度 → 扩充 18 个预检任务包 → 报告、文档及全量离线回归。用 TDD 逐项完成；正式模型评测等待用户确认规模和费用后再执行。

第一阶段完成只能声明“评测框架与离线验收已完成”，不能声明“真实缺陷评测完成”或“模型效果已提升”。

## 11. 后续阶段的固定约束

真实任务接入必须记录仓库 URL、buggy / fixed commit、Issue 或 PR 来源、许可、依赖锁定与测试范围；在隔离环境证明 buggy 失败、参考修复通过后才能纳入。

Docker 优先用于可复现的评测环境。Agent 生成与 grader 执行必须分开管理挂载和凭据；不能把整个宿主项目、参考资产或 LLM Key 挂给不可信测试代码。具体网络、资源和进程隔离在第二阶段设计中验收。

PyRepair 的输入是 pytest 故障，SWE-bench 的主要输入是 Issue。即便使用 SWE-bench 来源任务，也必须披露输入协议改造，不声称官方排名或官方成绩。

消融实验只改变目标机制，固定模型、预算、任务、环境和 grader。默认完整运行行为保持不变；没有结果前不预设 AST 上下文或反馈必然提高成功率。
