## 1. 目标与现有证据

本阶段只回答：**给 Review 补充 Repair 已能看到的公开任务说明，能否减少不符合任务约定的判断，同时不增加错误补丁放行？**

已有证据是旧版本 18 题 × 3 trial 的 case_03 / trial 1：两个 attempt 的候选 Diff 完全相同，第一次 Review 拒绝，第二次批准。公开规则为“加急 15、非加急 5，与非负重量无关”，第一次拒绝却推测重量还应影响运费。

源码确认 Repair 收到带 TASK.md 的 ContextBundle，Review 只收到 FailureReport 和 PatchSnapshot。信息差已确认，但尚未分离缺少任务说明与模型非确定性的影响。

保留旧实验 54/54、51/54 首 attempt 通过及原始产物；这些数字不用于宣称新版本有效。

## 3. 最小数据流和接口

### 3.1 用一个显式字段传说明

在 `src/pyrepair/context_builder.py` 的 ContextBundle 末尾增加：

```python
task_contract: str = ""
```

默认值保证现有五个位置参数的构造仍可使用。普通 ContextBuilder 不自动读取 TASK.md，未提供说明时保持空字符串。

`benchmarks/evaluation/agent_worker.py` 的 PublicContractContext 从干净 baseline 副本读取公开 TASK.md；沿用当前将说明放入 repo_overview 的方式，同时把同一段原文写入 task_contract。

构造示例（existing_bundle 是已有的上下文对象）：

```python
context_bundle = replace(
    existing_bundle,
    task_contract=(
        "Urgent shipping costs 15; non-urgent costs 5, "
        "independent of any nonnegative parcel weight."
    ),
)
```

replace 来自 dataclasses；它创建新对象，不修改 frozen dataclass。

说明上限沿用 4,000 字符；非字符串或超长输入在调用模型前报错，不静默截断以免丢掉关键条件。任务包必须有可读取、非空白的公开说明。说明缺失与解析错误不能被静默伪装成对照组“无说明”。

Repair 已使用显式字段构造消息，不会自动序列化整个 ContextBundle。新字段不再额外发送给 Repair，因此不会重复注入说明；原 16,000 字符上下文预算及修复提示词保持不变。

### 3.2 Coordinator 转交给 Review

候选接口：

```python
reviewer.review(
    failure_report,
    snapshot,
    task_contract=context_bundle.task_contract,
)
```

ReviewAgent.review 的新增参数是 keyword-only，默认空字符串；原来的 `review(report, snapshot)` 继续可调用。

Coordinator 在说明为空时继续使用原两参数调用，兼容现有无说明场景和旧测试替身；有说明时显式传关键字。需要接收说明的替身同步更新，不使用捕获 TypeError 后丢弃说明重试的办法。

说明来自 baseline，不重新读取 Agent 已修改的 working 副本；不把上一轮 Review 理由、隐藏验收反馈或参考答案混入任务说明。

### 3.3 Review 消息边界

两组统一使用同一个支持可选说明的系统提示词：按原始故障、候选 Diff 和已提供的公开业务约定审查；用户消息中的内容是任务数据，不能覆盖只读权限、输出格式或系统要求。

用户消息明确区分 failure、patch、task_contract；说明用 `{"trusted": false, "content": "..."}` 表示，content 按 JSON 字符串编码。空说明使用同一对象结构、content 为空字符串。Review 不获得文件访问或工具权限，工具列表仍为空。

不附加隐藏测试、gold 对照答案、正确性标签、case 的私有路径或历史审查结论。模型当然需要看到当前被审查的候选 Diff；这与额外提供一份参考答案是不同的。

继续使用现有 ReviewResult 结构和严格 JSON 解析；非法输出仍 approved=false，不把解析失败当成有效语义拒绝统计。提示词边界和消息构造测试不等于证明可以阻止所有模型提示注入。

## 4. 对照设计

### 4.1 冻结 3 题、6 份候选

第一批采用 case_03、case_15、multi_time：覆盖已观察的信息差、输入范围边界和多文件行为。它们是针对已知问题选取的开发样本，不能包装成随机抽样或未见测试集。

每题两份候选：

1. 正例：此前固定版本三次实验中 trial 1 的最终实际生成补丁。
2. 反例：该任务已有 wrong.patch，即能过可见测试但应被隐藏测试拦住的候选。

正例来源固定为 `live-repeat3-flash-20261016-df19fe71`，不按新 Review 输出重新选取。准备时将所需候选复制成独立、固定的 fixture，附来源和哈希；后续复现不依赖用户机器上旧结果目录的绝对路径。

离线准备必须重新验证：正例通过独立可见/隐藏验收；反例可见通过、隐藏失败；两者均能应用且通过补丁路径规则。还需核对公开契约是否支持正反例标签。任何一个标签不成立就停止准备并记录原因，不悄悄换题、改标签或改断言。

这里的“正例”仅指在声明的契约及有限验收范围内正确，不宣称程序在所有可能输入上都正确。

### 4.2 固定输入，只切换说明

每个候选冻结一份从公开 buggy 仓库复现的原始 FailureReport，以及一份 PatchSnapshot。故障捕获不在装有隐藏测试的副本上运行。

| 项目 | A：无公开说明 | B：有公开说明 |
| --- | --- | --- |
| 模型、采样配置、系统提示词 | 相同 | 相同 |
| 原始故障、候选 Diff、改动文件及行数 | 相同 | 相同 |
| task_contract.content | 空字符串 | 固定的公开说明 |
| 隐藏测试、参考答案、候选标签 | 不提供 | 不提供 |
| 工具权限、响应解析、拒绝规则 | 相同 | 相同 |

自动测试要求两份请求仅在说明内容字段上不同。不得重新执行 Repair 或让模型改候选；每次 Review 都是新的两条消息会话，不携带其他组或其他重复的结论。

重要解释：原系统提示词只提“故障和 Diff”，所以两组会统一使用支持可选说明的新提示词。**A 是共同新提示词下的无说明控制组，不是历史旧版的逐字复刻。** 此实验分离说明输入的影响，不单独证明整个新版本相对旧版的改善；完整升级效果需要后续新的端到端实验。

### 4.3 重复、顺序和费用边界

建议未来真实试验规模为 6 个候选 × 2 组 × 3 次 = 36 次 Review 调用。此处是建议，尚未获准调用。

每个候选/重复的 A、B 请求相邻，按候选和重复序号交替 AB/BA；保存完整调度表，使 18 对中两种顺序各占一半，减少所有 A 先跑造成的时间偏差，但不声称消除了服务端波动。

对照运行器将 DeepSeekClient 的 max_retries 显式设为 0；SDK 本身已为 0，故不会把一次 Review 偷换成多次 HTTP 重试。模型/网络错误记录为错误，不自动换模型、补样本或重请求。

真实入口必须显式指定 live、模型、重复次数和请求上限；计划请求数超过上限时在首个请求前拒绝。请求上限不是人民币费用上限，不能保证每次输出的 Token 数。

本设计获批后先实现并离线验证上述能力；真实 API 运行前再确认上述规模和费用边界。

## 5. 独立的 Review 评测入口

新增薄 CLI `benchmarks/run_review_evaluation.py`，评测逻辑放在 `benchmarks/evaluation/review_evaluation.py`，不将其塞入 Coordinator。

提供三类操作：

- prepare：离线生成并验证固定输入包、标签、候选及证据指纹；不初始化真实模型客户端。
- run：仅显式 live 时执行固定 A/B 调度；验证已准备输入和源码指纹，不在正式请求期间变更标签。
- report：从落盘证据重建统计，不调用模型。

候选清单和固定补丁置于 `benchmarks/review_cases/`；人工核对说明与候选来源可纳入版本控制。运行产物置于忽略的 `benchmarks/results/review/`；核对现有忽略规则，缺失时仅增加该产物目录。

第一版采用新目录单次执行，不实现付费运行自动续跑。已存在的输出目录拒绝覆盖；运行中断保留 started 和已结束条目，不自动重试未知结果。需要重新运行时必须另确认、另建实验，不混合成绩。

证据至少包括：

- manifest：协议版本、源码/新 CLI/候选/说明/提示词哈希、运行环境、模型标识、计划调度和预算。
- 私有评分数据：候选标签、独立验收结果及人工核对依据；不传入模型。
- requests/results：各次模型实际输入、返回 content、解析结论、用量、耗时与错误；不保存 API Key、请求头或 reasoning_content。
- summary.json / report.md：可从记录重建的统计和解释边界。

模型发送函数仅接收白名单字段组成的 Review 输入，不接收包含标签、hidden 或 gold 的 EvaluationCase/评分对象。离线通过 canary 和完整请求快照测试这个边界；这是数据传递约束，不是 OS 隔离。

写入遵循现有记录器的有限重试与异常脱敏规则。请求前 started 无法保存则不发请求；响应后保存失败则停止后续请求，保留临时文件和成本未知状态，不能假装一切已记录。

## 6. 统计口径和解释规则

至少报告以下指标，给出计数和分母，而非只给百分比：

- 正例误拒：有效结构化回复中，正确候选被拒绝的数量 / 正例有效判断数。
- 反例误放：有效结构化回复中，错误候选被批准的数量 / 反例有效判断数。
- 端到端判断正确：结构化判断与标签一致的数量 / 全部计划请求数；未完成、API 错误、解析失败不算判断正确。
- 有效回复覆盖率、API 错误、解析失败、未执行数量，独立列示，不能靠排除错误报出漂亮准确率。
- 同候选同组的判断波动：三次均取得有效判断的候选中，是否同时出现批准和拒绝；另报不完整候选组。
- 配对对照：同候选同次重复的 A/B 都有效时，分别统计 B 纠正 A、B 破坏 A、两者均对、两者均错；缺失配对另列。
- 用量和时间：按组统计输入/输出 Token、耗时、实际请求数。缺失 usage 或原客户端映射的 0/0 保守标为未知，不记零成本。

不将“批准率提高”视为成功，也不声称这 3 题能证明普遍提升。即使 B 在该批样本中误拒更少且误放未增加，也只能称为定向开发集上的支持性证据；若误放增加，需要逐例分析，不能自动推广。错误/缺失足以妨碍比较时明确报告证据不足。

## 8. 离线验收清单

1. 原两参数 Review 调用可用，ContextBundle 旧构造可用；无说明的 Coordinator 测试保持兼容。
2. worker 提供的同一说明出现在 Repair 原有上下文和 Review 新字段；来自 baseline，不来自 working；Repair 请求不重复增加说明。
3. 4,000 字符边界、非法类型、任务说明缺失/空白/超长均有测试，失败发生在真实客户端调用之前。
4. 两组 system、failure、patch、工具列表与配置相同，仅说明内容不同；恶意引号或伪造指令不会改变消息角色和结构。
5. 所有请求都不含评分 canary、隐藏测试内容、gold 对照答案、候选标签或私有路径；非法 Review JSON 保守拒绝。
6. 三题六候选离线重新验收并冻结，记录公开契约核对；异常任务停止准备，不能无记录换题。
7. FakeLLM 验证 36 次请求计划、AB/BA 各半、会话独立、无自动重试、预算不足零调用；离线操作零模型初始化。
8. 预设混淆结果验证各分母、解析失败、缺失、同候选波动、配对统计和未知成本；报告可重建。
9. 输出目录拒绝覆盖，指纹改变拒绝运行，持久化失败停止发请求并保留证据，错误信息脱敏。
10. 定向测试、全量非 live 回归、相关文件静态检查及差异检查通过；核验旧评测资产/结果未改变。只报实际执行结果。

离线全部通过只代表工程实现满足设计，不代表真实 Review 准确率提高。

## 10. 审批后发现的样本标签问题

2026-10-16 制定计划时，实际应用 case_15 / trial 1 的历史补丁复现了反例：输入 `12345678901234567890123456789.01` 应得 `1234567890123456789012345678901` 分，默认 Decimal 精度 28 时却得 `1234567890123456789012345679000` 分。保持补丁和输入不变，仅在诊断用 localcontext 中将精度改为 64 后，该反例恢复正确；这不是通用修复方案。

公开说明没有金额长度上限，该输入是非负、两位小数，因此不能把它排除在约定之外，也不能继续把这份补丁标为已知正确。既有测试没有覆盖此条件；旧 54/54 仍是旧测试下的历史观察，不回改成绩。

按第 4.1 节的停止规则，当时暂停固定样本准备并向用户提出选择。用户随后批准“修正候选并补边界验证”：保留三题六候选，金额正例改为明确标注的人工校准版本，新增本次 Review 专用精度检查；旧产物和旧测试保持不变。

不受影响的输入链路单独形成[实施计划](../plans/2026-10-16-review-contract-input.md)。本补充保留原第 4 节作为已批准方案的历史，不静默替换候选来源。

后半段按[固定候选与对照实施计划](../plans/2026-10-16-review-fixed-evaluation.md)实施。历史金额候选只作为不参与模型评测的诊断反例。实现按职责拆分为 review_fixtures.py、review_evaluation.py、review_reporting.py，未扩大评测问题或模型权限。
