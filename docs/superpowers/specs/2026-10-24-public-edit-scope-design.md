# 共享公开文件修改范围设计

日期：2026-10-24。状态：用户回复“好的”批准后，已完成离线实施与验收，详见[离线记录](../../public-edit-scope-offline.md)。批准不包含真实模型调用。

授权范围：用户“继续吧”同意继续离线补齐两方法共享的文件范围约束。本文细化实施边界；不包含任何新增模型请求、旧额度复用或 Git 发布。沿用 evaluation-v2 工作区，不动 main，不提交本文。

## 1. 问题与目标

[最新真实冒烟](../../controlled-live-comparison-smoke-after-fixes.md)中，single-shot 修改了 `more_itertools/__init__.py`，评分器只允许 `more_itertools/more.py`，因而在执行功能测试前拒绝候选。当前两方法的初始材料虽然相同，却都没有明确获知这个限制。这不是已经证明模型不会修复，也不能通过放宽评分把旧候选改成成功。

目标是让两方法在首次模型调用前看到**同一份、与评分器精确一致的文件修改范围**，并让完整工作流的 Review 同样获得它。保持当前任务、隐藏测试、补丁判分和 Agent 循环不变。

## 2. 两种实现方式与推荐

| 方式 | 做法 | 取舍 |
| --- | --- | --- |
| A，推荐 | 准备公开输入时，在 `TASK.md` 顶部生成统一的文件范围规则；沿现有上下文链路传给两方法与 Review | 不增加生产 Agent 参数，不扩展 worker 描述字段；需要验证公开文本与评分清单一致 |
| B | 给 `PublicTaskSpec` 增加结构化范围字段，再给两方法和 Review 分别装配提示词适配器 | 约束更显式，但要同时修改描述协议、调用适配和更多边界测试；目前没有必要扩大范围 |

采用 A。不是只给失败的 single-shot 增加提示，也不删去其他可读源码来改变检索难度。公开范围会提供文件级线索，因此新报告要注明这是**已告知可修改文件范围**的评测，不宣称在未知完整仓库中独立定位。

## 3. 唯一来源与公开文本

在 `benchmarks/evaluation/agent_input.py` 增加一个纯生成函数，由已验证的 `EvaluationCase.allowed_source_paths` 和原公开任务说明构造展示文本。该函数不读取 private、gold、wrong、隐藏节点或隐藏测试内容。

例如 more 任务的公开前缀为：

```text
## 公开评测约束（agent-public-r2）
允许修改的现有源码文件（相对仓库根目录，精确文件路径；不是目录或通配符）：
["more_itertools/more.py"]

补丁只能修改以上文件，不得新增、删除或重命名文件。
其他公开文件仅可通过原有工具权限读取，不得修改。
不得修改测试、配置、依赖或环境。

## 原始公开任务说明
……既有任务说明……
```

路径采用 JSON 数组序列化，保持 manifest 顺序，防止路径引号、空格或换行被误当作多条规则。所有路径必须通过现有安全相对路径检查，属于现有、未过滤且不受保护的源码文件；重复、大小写碰撞或不合法输入直接拒绝。多文件任务完整列出全部允许文件，不缩减到单文件。

展示文本统一使用 LF；原始 description 资产不改写。只替换新建公开副本的 `TASK.md`，其他公开文件仍保持字节一致，不规范化源码换行。

组合后的**整份**说明仍受既有 4,000 字符限制约束。空任务、非法 UTF-8、路径无效或长度超限应在复制/模型构造前报错；不截掉规则或任务，不自动扩大上下文预算。现有 20 题冻结说明为 174–474 字符，仍须对实际组合结果逐题检查，不能以此估计代替验收。

## 4. 现有链路与文件职责

```text
控制器已验证的 allowed_source_paths ＋ 原公开任务说明
  → agent_input：生成并验证 TASK.md，计入公开输入摘要
  → PublicContractContext：放入 repo_overview 与 task_contract
  → 冻结公开 evidence
      ├─ single-shot：initial_facts → 首次用户消息
      └─ full-agent：同一 initial_facts → RepairAgent
                    同一 task_contract → Coordinator 装配 Review 输入

独立评分：仍使用原 EvaluationCase.allowed_source_paths，不从模型文本取规则
```

- `agent_input.py`：生成文本、前置验证、公开输入策略升级到 `agent-public-r2`。`PublicTaskSpec.version=1` 及字段集合保持不变，因为结构未变；旧 r1 描述不接受为新输入。
- `agent_worker.py` 的 `PublicContractContext`：复用原规则，整份任务说明保留；总上下文超过 16k 时只按既有逻辑减代码片段，不截任务前缀。是否需要代码改动以测试结果为准。
- `comparison_evidence.py` / `comparison_methods.py`：保留共享事实和相同初始用户消息；不给某一方法追加专属规则，不更改 single-shot 一次响应或 Agent 工具预算。
- `comparison_pack.py`：公开事实策略标识升级到 `exact-public-facts-r2`。准备与核验均核对 `TASK.md`、evidence 中的任务文本与统一生成结果一致，避免公开范围与评分器不同。缺少/不匹配在任何模型构造前拒绝。
- `review_agent.py` 与生产 `src/pyrepair/`：不改接口和行为；通过既有 `task_contract` 获得同一份完整说明。

任务/仓库数据仍是待处理证据，不把整个 `TASK.md` 提升为可覆盖系统要求的指令。文件范围只是一项公开评分事实；它不开放额外工具权限，也不替代评分器的确定性检查。不得为了让模型遵从而移除现有不可信数据标记。

## 5. 不改变的内容与历史边界

1. 不改 allowed_source_paths 清单、评分器、80 行门禁、核心/扩展范围、gold/wrong、隐藏测试、任务 revision 或原始资产。
2. 不改生产 Repair/Review 提示词、Agent Loop、工具能力、完成条件、模型配置或调用预算。
3. 不把旧候选改路径或重新判分；旧两轮真实冒烟、失败、消耗及原始报告只读保留。
4. 新的公开前缀是模型输入变化，必须产生新公开摘要、运行源码摘要和冻结包身份。旧包不得原地更新或续跑；历史结果与 r2 新结果分开，不混合统计。
5. 这一改动只解决规则事先公开，不保证模型遵从或提高成功率。效果需要以后另行授权的真实运行验证。

## 6. 离线验收顺序

先写反例测试，确认旧实现缺少范围规则，再最小实现；集中验证，不逐个任务拆代理或重复跑完整套件。

1. **文本与输入边界**：单文件、多文件、特殊路径序列化；空任务/超长/非法路径/碰撞拒绝；原始资产不变、无隐藏数据进入公开副本。
2. **共享输入一致**：FakeLLM 捕获 single-shot 与 Repair 首次用户消息，逐值相同且包含准确清单；捕获 Review 消息，含同一完整任务说明。不以仅断言某个单词存在代替路径集合一致。
3. **截断反例**：接近 16k 的上下文，允许减代码片段，但全部范围规则和任务说明仍在；组合说明超 4k 必须拒绝，不能静默截断。
4. **冻结及失配反例**：缺失/篡改公开约束、不同任务的范围、旧 r1 策略均拒绝；正常 r2 生成与核验通过，拒绝发生在模型 client 构造之前。
5. **评分不变**：原规则仍拒绝 `__init__.py` 越界补丁；合规补丁仍按既有流程验收。只验证这条规则，不重跑或改分历史候选。
6. **集中回归**：相关单元/集成、一次完整非 live/non-Docker 回归、静态检查，以及现有 FakeLLM＋真实 Docker 的限定链路验收；清除子进程 key，不在宿主执行上游测试。
7. **新冻结检查点**：上述通过后，使用相同 18 合成＋2 开源、既有环境锁和评分清单，在新目录完成实际离线校准、冻结核验、120 脚本槽位与恢复检查。模拟不是模型成绩；若失败保留证据，不选择性补跑。

每步问题、原因、处理和实际验证结果追加到[工程日志](../../evaluation-v2-engineering-log.md)。未通过的步骤不标完成；如现有链路无法满足设计，先报告原因，不擅自改成 B 或更改生产逻辑。
