# Review hard v1：72 次真实 A/B 对照

运行日期：2026-10-19，北京时间约 15:38:06–15:45:13。模型请求标识：`deepseek-flash`。

## 结论

六个自建开发任务、十二份固定候选、两组各重复三次：

- A 不提供公开任务说明：判断正确 **24/36（66.7%）**。
- B 提供公开任务说明：判断正确 **32/36（88.9%）**。
- B 相比 A 纠正 8 对判断，没有出现 A 对而 B 错的配对；另有 4 对共同错误。
- B 的错误补丁误放为 **4/18（22.2%）**：金额精度反例三次全部误放，时区辅助函数反例一次误放。
- 72 次均有效，无 API/解析错误、缺失、自动重试或补样；记录用量 **113,664 Token**。

结论不是“Review 已可靠”。本次结果表明：公开说明有助于界定任务要求，但不能替代独立测试，尤其不能保证发现数值精度和辅助接口问题。这是固定候选的审查判断，不是 Repair 生成补丁的成功率。

## 4. 有价值的发现

### 4.1 任务说明能补充测试未展示的要求

case_13 反例只调用 lower，没有 strip。A 三次都批准，并把首尾空白当作当前故障未要求的边界；B 三次都根据公开说明中的空白要求拒绝。三对差异均由 B 纠正。证据：[A 请求 0020](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0020/result.json)、[B 请求 0019](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0019/result.json)。

multi_time 正例中，A 三次都担心 naive 时间和非 UTC 参数等更宽输入域；公开契约排除了这些情况，B 三次都批准。这是另外三对纠正，不是证明那些担忧在所有场景下都无效。证据：[A 请求 0061](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0061/result.json)、[B 请求 0062](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0062/result.json)。

### 4.2 使用 Decimal 不等于算术永远精确

金额反例使用 `int(Decimal(value.strip()) * 100)`。模型两组三次均批准，B 的理由还明确认为对最多两位小数的输入，该运算精确。但小数位数限制并没有限制整数部分长度；Decimal 乘法仍受 context 精度影响。

在精度 28 时离线复现：

```text
输入：12345678901234567890123456789.01
应得：1234567890123456789012345678901
实得：1234567890123456789012345679000
```

输入属于既有公开契约，并非看到答案后新加要求。调用前的独立隐藏验收已确定该候选错误；不因模型全部批准而更改标签。证据：[B 请求 0031](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0031/result.json)、[B 请求 0034](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0034/result.json)、[冻结前离线验收](review-hard-candidates-offline.md)。

### 4.3 主流程通过，不等于公开辅助接口正确

时区反例在 formatter 内转 UTC，整体 normalize 的例子通过，但 parser 仍返回原偏移。公开说明要求 parser 自身返回 UTC aware datetime。

A 三次均批准；B 第一、三次识别该接口违约，第二次仍只根据主流程批准。因此 B 在这里纠正两对，但仍有一次误放。证据：[B 第一次拒绝 0067](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0067/result.json)、[B 第二次批准 0070](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0070/result.json)、[B 第三次拒绝 0071](../benchmarks/results/review/live-hard-ab72-flash-20261019-01/requests/0071/result.json)。

部分回复自行提到可能的 hidden tests，这是模型基于公开契约的推测，不是获得了私有测试；实际 72 份请求已逐一核对输入白名单。

## 7. 能说明什么，下一步做什么

1. 新反例不再全是明显硬编码，确实暴露了 Review 误放；不能沿用旧六候选“反例零误放”概括当前能力。

3. 部分正确参考经过人工校准。本轮只审查固定补丁，不能把 32/36 写成模型代码修复成功率，也不能合并进旧 54 次端到端统计。
4. 不应为得到更好数字而改本轮标签、删掉金额反例或补跑时区题。本轮 72 次授权已用完，旧成绩保留。
5. 后续优先引入独立真实缺陷和冻结未见任务，再考察数值边界与公开辅助接口；若开发通用契约审查清单，应在开发集调试、在独立留出集验证，而非只重考这六题。
