## 1. 和上一版有什么不同

上一轮是真实运行的三题六候选、36 次 Review A/B，对照结果见[旧报告](review-contract-live-results.md)。本轮不覆盖它，而是新增一个独立集合：

- 从既有 18 个 synthetic/dev 任务里选择六题，固定十二份候选，并非新增六个独立任务。
- 每题一份正确参考、一份非单样例硬编码错误。前三题检查边界、归一化和精度，后三题涉及多文件接口或状态。
- 错误补丁必须先通过可见测试，再由独立隐藏断言复现契约内的错误；不能用环境错误、漏测试或跳过测试冒充成功识别。
- 增强隐藏验收只保存在新目录；原公开契约、源码、测试、旧参考和旧成绩都保留。

仍是定向开发挑战集，不是 holdout，也不是真实开源缺陷。两道较简单的边界题用于校准，不把全部六题宣传成复杂真实仓库任务。

## 2. 实际标签校准结果

下表的“通过/识别”来自真实 pytest 子进程，不是模型判断。每个正反候选均在独立临时副本应用；可见测试均通过，隐藏测试全部收集执行。

| 任务 | 每份可见/隐藏测试数 | 正确参考 | 错误补丁的隐藏断言失败数 | 判别点 |
| --- | ---: | --- | ---: | --- |
| case_04 | 2 / 3 | 全通过 | 2 | 第 0 页和空总页数不能有效 |
| case_13 | 2 / 3 | 全通过 | 2 | lower 不等于 strip + lower |
| case_15 | 2 / 20 | 全通过 | 6 | Decimal 乘法会受 context 精度影响 |
| multi_orders | 1 / 4 | 全通过 | 1 | 总额折扣后取整，不等于逐项取整再求和 |
| multi_inventory | 1 / 7 | 全通过 | 1 | 超量预订抛错后库存不能变 |
| multi_time | 1 / 4 | 全通过 | 1 | 主流程正确，仍可能违反公开 parser 的 UTC 契约 |

六份正例共 41 项次隐藏测试全部通过；六份反例执行 41 项次，其中 13 项次为真实 AssertionError，其余 28 项次通过。十二候选共 18 项次可见测试通过。金额的 20 项中包含六个金额 × 三种精度的 18 项精度边界。

此外，六题的 buggy / reference / mutant 预检均有效：声明的 fail-to-pass 在原始版本失败、pass-to-pass 原本通过。并非只检查补丁后的版本。

### 两个具体例子

订单：`[(1, 1), (1, 1)]` 的 vip 总额应为 `(1 + 1) * 80 // 100 = 1`；错误写法逐项算 `1 * 80 // 100` 再相加，得到 0。公开示例使用整百金额，看不出这个差异。

库存：库存为 3，预订 4 应抛 ValueError，而且库存仍为 3。反例先扣成 -1 再抛错，因此虽然可见的“预订成功再取消”通过，独立验收仍能识别失败操作的副作用。

### 来源不是模型成绩

- 金额正例复用此前人工校准的 `Decimal.as_integer_ratio()` + 整数运算方案。
- 金额反例是旧集合已排除的历史精度反例；只在本新集合成为正式负例，旧排除记录不变。
- 时间正例复用历史模型候选；其余正例是人工参考或人工校准，负例是契约导向人工变异。
- 来源、原始 SHA-256、机制分类和理由见[候选清单](../benchmarks/review_cases_hard_v1/manifest.json)。

## 3. 哪些信息给模型，哪些不给

Review 的业务输入仍只有：公开 baseline 故障、当前候选的源码变化/Diff、可选公开任务说明。

A 组不附说明，B 组附同题公开说明；系统提示词、故障和候选保持一致。其他候选的参考答案、正反标签、来源、分类、隐藏测试及其执行结果不进入消息。先在仅含公开文件的副本捕获 baseline，不能安装隐藏验收后再拿失败日志喂模型。

本轮用 FakeLLM 实际验证十二候选 × 两组 × 三次 = 72 个独立请求，以及请求中没有私有 canary、每对消息仅说明字段不同。**72 是模拟调度次数，不是新增付费调用或真实准确率。**

## 4. 准备包与资产绑定

[review_assets.py](../benchmarks/evaluation/review_assets.py) 将实际选中的 fixture 目录、任务 manifest 和所选任务资产绑定到准备包；仓库内采用相对位置，外部临时集合明确使用绝对位置。

- 改动补丁、说明、源码、隐藏验收、清单，或缺失声明文件，均应在初始化模型客户端前拒绝，要求重新准备。
- 显式声明的补丁、precision_test 和 hidden_tests 不能因位于通用忽略目录而漏哈希。
- 执行前后还检查实际运行的验收副本；候选修改/删除验收文件，或将其替换为链接，会使准备失败。
- 准备开始与结束都核验，防止运行中资产变化后仍输出 ready 包。
- 旧无 asset_binding 的准备包保留旧读取分支；源码变化使旧 ready 包不能直接用于新 live 调用，是预期保护。
- 历史 run 的离线报告不依赖当前 runtime 相同；旧 36 次报告已经在副本重建，summary.json 与 report.md 逐字节一致。

SHA-256 是误改检测和复现依据，不是防恶意篡改的数字签名；前后检查也不能防御篡改后恢复等主动攻击。临时副本不是 OS 沙盒；只运行可信自建资产。

## 5. 如何复现（不调用模型）

在 evaluation-v2 worktree 中，用项目虚拟环境的 Python，或已正确安装当前工作区的环境运行：

```powershell
python benchmarks/run_review_evaluation.py prepare --manifest benchmarks/manifest_review_hard_v1.json --fixtures benchmarks/review_cases_hard_v1 --output benchmarks/results/review/my-hard-prepared
```

输出目录必须不存在，避免覆盖证据。成功后重点看：

- `prepared.json`：冻结的输入、标签、元数据、来源、资产摘要与验收结构。
- `baselines/<case>.log`：六个公开原始失败。
- `grading/<candidate>/grade.json`：可见/隐藏状态、全部测试节点和真实断言证据。
