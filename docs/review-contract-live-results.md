### 两次差异的具体原因：模型不知道输入范围

multi_time 正例修改两个文件：解析时用 astimezone(timezone.utc) 保留真实时刻，格式化时输出约定的 Z 后缀。

公开任务已规定：

1. normalize 只接收包含时区偏移的有效 ISO-8601 时间字符串，允许 Z。
2. 无时区的 naive 输入不在任务契约内。
3. parse_timestamp 输出 UTC aware datetime；format_utc 的输入约定也是 UTC aware datetime。

A 的请求 **0025、0029** 都指出了真实的潜在边界问题：naive 时间经过 astimezone 会按宿主本地时区解释；如果直接向 format_utc 传入非 UTC 时间，字面量 Z 可能误导。**这些担忧在更宽的 API 契约下是有道理的**，但这两个输入类别已被本任务明确排除，因此在预先冻结的契约内标签下计为误拒。

B 的对应请求 **0026、0030** 看到了约定，认为这些情况在范围之外，批准同一份补丁。说明不是让 Review 忽略风险，而是让它按已声明的边界判断风险。不能在看到结果后临时缩小契约来让某个补丁变“正确”；本次契约与标签在运行前已冻结。

## 6. 局限与下一步

1. 三题按已知问题挑选，是 synthetic/dev，而非随机样本、冻结 holdout 或真实开源缺陷；同一候选重复三次并未增加任务多样性。
2. 三个反例主要是明显的单样例硬编码，两组都拒绝，无法充分检验对隐蔽错误的识别能力。0/9 误放不等于普遍不会误放。
3. 金额正例是人工校准，不能计入模型新修复成绩。原历史补丁的长金额反例、旧 54/54 有限测试成绩均原样保留。
4. 本次只测试 Review 判断，不能替代接入新说明链路后的端到端修复评测，也没有证明不同模型或更大仓库的效果。
5. 公共任务说明必须真实且由可信流程提供；它在模型输入中仍是任务数据。提示词隔离和白名单不构成完整的提示注入防护或 OS 沙盒。

建议保留这一实现和实验作为定向证据。下一阶段优先**另建一套更难、固定的候选集**：覆盖边界条件、遗漏分支、多文件不一致等非硬编码错误，再对开发/留出样本明确分组。不要为了让本轮差异更大而修改已冻结的六候选；新任务、新预算与端到端运行另行确认。

面试可以表述为：“我发现 Repair 与 Review 的任务信息不对称，增加公开契约传递，并做了固定补丁 A/B 对照。在三题六候选的 36 次调用中，有说明组少了两次契约外误拒，未观察到反例误放增加；同时保留小样本和人工候选的限制。”不要简化成“Review 准确率达到 100%，真实缺陷全部修复”。
