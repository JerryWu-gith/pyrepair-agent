## 不应被 100% 掩盖的发现：Review 会误判

### case_03 / trial 1：同一个 Diff，先拒绝再批准

两次候选 Diff 逐字相同，都是将 `if urgent and weight_kg > 10:` 改为 `if urgent:`。

- 第一次 Review 拒绝，推测正确规则可能是“加急或重量超过 10kg 都收 15”。
- 第二次 Review 批准同一份补丁。
- 公开任务契约 `benchmarks/eval_descriptions/case_03.md` 明确规定：加急收 15、非加急收 5，与非负重量无关。隐藏验收也检查了非加急重包裹仍收 5。

因此，首次拒绝理由与已声明契约冲突。不能把这次重试宣传为“审查发现并修好了一个错误补丁”；它实际上增加了一轮修复和模型消耗。

源码边界已核对：`coordinator.py` 向 Review 传入的是 `failure_report` 和 `snapshot`；`review_agent.py` 构造的消息包含原始故障和 Diff，**没有传入评测公开任务契约**。Repair 的上下文适配器则包含公开任务契约。这个信息差是值得验证的风险点，但尚未通过对照实验分离“缺少任务上下文”和“模型非确定性”的影响，不能声称唯一根因已经被证明。

### case_15 / trial 1、3：审查触发了不同候选

这两次的首次 Review 提出负号处理、空输入等边界风险，下一 attempt 的最终补丁改为使用 Decimal 计算，随后通过验收。该任务公开契约主要限定非负、最多两位小数输入，部分审查意见属于契约之外的兼容性关注；仍不能只凭这两条轨迹声称 Review 整体效果提升。

**总体成功率、审查准确性、重试成本是不同指标。** 本轮的 0/54 Agent 误报不包含 Review 误拒绝，不能据此说 Review 判断 100% 正确。

本轮没有修改 Review。后续可针对“向 Review 提供同一份公开任务契约”做单变量对照，并记录误拒绝和额外调用成本；不能把隐藏断言作为审查输入。
